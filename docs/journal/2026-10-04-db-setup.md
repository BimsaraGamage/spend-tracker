# 2026-10-04 · Phase 1: database setup

### D-115 · Harden the generated Supabase configuration (autopilot)

- **Decision:** Change these `supabase init` defaults (autopilot):
  - minimum password length 6 → **12**, with no composition rules (NIST SP 800-63B: length matters, "must contain a symbol" rules don't);
  - email confirmation required on password sign-up;
  - recent sign-in required before changing a password;
  - one-time codes valid for **10 minutes**, not 1 hour, and resends throttled to **60 s**, not 1 s;
  - TOTP two-factor enabled server-side (D-10);
  - only the `public` schema exposed through the API, not `graphql_public`;
  - Realtime, Storage, Edge Functions and Analytics switched off, since they aren't used yet (sync is PowerSync's job).
- **Why:** The generated defaults are tuned for local convenience. A finance app's baseline must be secure (ADR-0009, SEC4). Fewer running services means less attack surface and faster CI.
- **Note:** This file configures the _local_ stack. The hosted projects get the same settings when they're created (Phase 1 deploys).

### D-116 · Internal `private` and `audit` schemas, with no default execute rights (autopilot)

- **Decision:** (autopilot)
  - **Helpers:** functions used by RLS policies and triggers live in `private`.
  - **Audit log:** it lives in `audit` (DATA7). Clients have no access at all.
  - **Function rights:** every function in these schemas revokes Postgres's default "everyone (PUBLIC) can execute" explicitly. A guard test fails the build if one is forgotten (see D-120).
- **Why:** Supabase's API exposes `public`. Internal functions placed there could become callable endpoints.
- **Tested:**
  - A pgTAP guard checks that every `public` table has RLS (SEC1), and checks itself by detecting a deliberately unprotected probe table.
  - Further tests check that neither client role can reach the internal schemas or execute helpers.

### D-117 · Database tests in CI (autopilot)

- **Decision:** A `database` CI job:
  - installs the Supabase CLI (pinned 2.119.0, through `supabase/setup-cli` at a pinned SHA);
  - starts only Postgres and Auth;
  - runs `supabase test db`.

  It is part of the `required` gate (autopilot).

- **Why:**
  - The maintainer's machine has no Docker, so CI is where database tests run.
  - Auth is needed because it creates the `auth` schema the policies rely on. Every other container is excluded to keep runs fast.
  - The CLI's telemetry respects `DO_NOT_TRACK`, which CI already sets.

### D-118 · Lesson: a checksum check that silently didn't run

- **What happened:** Verifying the downloaded Supabase CLI, `grep … | sha256sum --check` matched no line, because the checksum file lists the versioned filename. Without `set -o pipefail`, the script carried on and extracted the binary. The binary was then **verified properly before use**: its SHA-256 matched the published value for the identical versioned asset.
- **Lesson:**
  - `set -e` doesn't cover pipelines unless `pipefail` is on.
  - A security check must be an explicit `if` that stops the script, never a side effect of shell options.

### D-119 · Lesson: `supabase migration new` reads standard input

- **What happened:** The command hung. Without a terminal it waits for SQL on standard input. Looking at the running process showed the file already created and the CLI blocked on input, so the process was stopped and the file written directly.
- **Lesson:** When a non-interactive command hangs, inspect it (processes, files, output) before retrying. Give interactive-capable tools `</dev/null`.

### D-120 · Correction: a per-schema default-privilege revoke does nothing (autopilot)

- **Found by:** The first CI run of the database tests. The test "helper functions are not executable unless granted explicitly" **failed**: signed-in users could execute `private.set_updated_at()`.
- **Cause:** PostgreSQL documents that a per-schema `ALTER DEFAULT PRIVILEGES … REVOKE` can't remove a _global_ default, and every new function is executable by `PUBLIC` by default. The migration line looked protective but had no effect.
- **Decision:** (autopilot)
  - Revoke `PUBLIC` execute explicitly on every internal function.
  - Replace the single-function check with a guard over **all** functions in `private` and `audit`: no client role may execute any of them, apart from an explicit allowlist for signed-in users (needed later by RLS helpers).
  - The guard checks itself with a probe function that keeps the default rights.
  - The migration was corrected in place. It had never been applied to a persistent database, only to throwaway CI ones (DB1 protects _applied_ migrations).
- **Lesson:** Security settings that "look right" must be tested. A test that checks the _effect_ (who can execute) caught what reading the code missed.
