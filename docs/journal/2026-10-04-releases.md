# 2026-10-04 · Releases

### D-102 · release-please through a release-bot GitHub App, inactive until configured (autopilot)

- **Decision:** release-please (pinned v5.0.0) runs as a dedicated GitHub App:
  - its token comes from `actions/create-github-app-token` (pinned v3.2.0, using `client-id`; `app-id` is deprecated in v3);
  - the token has only three permissions: contents, pull requests and issues;
  - the workflow skips with a notice until the app is configured.

  The single-version config starts at `0.0.0`: features bump the minor version, fixes the patch version, and breaking changes bump the minor version until 1.0. Only feat, fix, perf and revert appear in the changelog.

- **Why:**
  - PRs opened with `GITHUB_TOKEN` don't trigger CI, so a release PR could never pass the required check.
  - An app token is short-lived, scoped to this repository, and isn't tied to a person or a device.
- **Risk to check:** GitHub signs app-created API commits only if they carry no custom author or committer details. If the first release PR shows unverified commits, the signed-commits rule blocks it (see D-93), and this setup needs revisiting.

### D-103 · Keep the release bot's key in a branch-restricted environment (autopilot)

- **Found by:** zizmor's strictest "auditor" level: `secrets-outside-env`.
- **Decision:** The release job uses a `release` environment that accepts deployments from `main` only. The bot's Client ID and private key live there, not as repository-wide secrets (autopilot).
- **Why:** Repository secrets are available to workflows on any branch. Environment secrets are released only to jobs running on the allowed branches, so a workflow edited on a feature branch can't read the key.
- **Pending:** Creating the environment is a settings change, so it waits for the maintainer's approval (AGENTS.md).
- **Lesson:** Run security scanners at their strictest level at least once. The default level is tuned to avoid noise, and that can hide improvements that cost one line.
