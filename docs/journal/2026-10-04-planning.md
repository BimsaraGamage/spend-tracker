# 2026-10-04 · Planning

Project planning decisions are grouped by topic. ★ marks the recommended option recorded at the time.

## Round 1: product and data fundamentals

### D-01 · What the data model supports

- **Prompt:** The working folder was named "revenue-tracking" but the idea was a spend tracker. What should the data model support from day one? Features can still ship gradually.
- **Options:** ★ Income + expenses ledger · Expenses only · Full personal finance · Business revenue/costs
- **Decision:** Full personal finance (maintainer).
- **Action:** The data model covers accounts, transactions, transfers, categories, budgets, recurring items and savings goals; features ship incrementally.
- **Lesson:** Decide the scope of the _data model_ separately from the scope of the _first release_. A wide model with a narrow UI costs little; reshaping a narrow model later is a data migration.

### D-02 · Where the financial data lives

- **Prompt:** Where should the data live? This drives security, cost, offline behaviour and how others can use the app.
- **Options:** ★ Cloud DB, offline-ready · Local-first + sync · Device-only, no server · End-to-end encrypted sync
- **Decision:** Local-first + sync (maintainer).
- **Action:** Each device keeps its own SQLite database, synced to Postgres (the source of truth) by a sync engine. The UI reads and writes locally, so it works offline and feels instant.
- **Lesson:** A sync engine's main cost is in edge cases (conflicts, schema changes reaching offline devices, rejected uploads), not the happy path.

### D-03 · Who owns the data rows

- **Prompt:** Should data belong to individual users, or to ledgers that users are members of? It decides whether shared budgets need a migration later.
- **Options:** ★ Ledger with members · Strictly per-user
- **Decision:** Ledger with members (maintainer).
- **Action:** Every row carries a `ledger_id`. Each user starts with a personal ledger, and access is granted through membership with roles.
- **Lesson:** Tenancy boundaries are a one-way door. Model the boundary you might need, even if you start with one user per ledger.

### D-04 · How others will use the app

- **Prompt:** When the app opens to others, will they use a hosted instance, run their own backend, or both?
- **Options:** ★ Hosted + self-host · Hosted instance only · Self-host only · Decide later
- **Decision:** Hosted + self-host (maintainer).
- **Action:** No hard-coded endpoints: backend URLs come from configuration, and a self-hosting guide is on the roadmap.

## Round 2: technology stack

### D-05 · Client framework

- **Prompt:** Which client framework should build the app? They differ in how mature the web build is and how native the mobile app feels.
- **Options:** ★ Expo universal app · Web PWA now, Capacitor later · Separate web + native apps · Flutter
- **Decision:** Expo universal app (maintainer).
- **Action:** One React Native + TypeScript codebase for iOS, Android and web. Shared packages keep a fallback open: a separate web app, if the web build of the sync engine (beta at the time) disappoints.

### D-06 · Backend

- **Prompt:** What should run the server side (authentication, validating uploaded changes, the master copy)?
- **Options:** ★ Supabase + PowerSync · Rails 8 API + PowerSync · TypeScript API + PowerSync · Zero (Rocicorp) + Postgres
- **Decision:** Supabase + PowerSync (maintainer).
- **Action:** Supabase provides Postgres, Auth and Row Level Security. PowerSync streams only the ledgers a user belongs to. Uploaded writes are checked by RLS, constraints and SQL functions.

### D-07 · Repository shape

- **Prompt:** How should the repository be structured?
- **Options:** ★ pnpm + Turborepo monorepo · Single app with folders · Nx monorepo
- **Decision:** pnpm + Turborepo monorepo (maintainer).
- **Action:** `apps/` for applications and `packages/` for shared code. The pure domain core has no UI or I/O dependencies.

### D-08 · Test phones

- **Prompt:** Which phone will be used day to day before any store launch?
- **Options:** Android · iPhone · Both
- **Decision:** Both (maintainer).
- **Action:** Before store enrolment, Android uses directly installed builds and the iPhone uses the installable web app (PWA).

## Round 3: security, hosting, cost

### D-09 · Sign-in methods (multiple choice)

- **Prompt:** Which sign-in methods should v1 support?
- **Options:** ★ Email one-time code · Google · Sign in with Apple · Email + password
- **Decision:** All four (maintainer).
- **Action:** Email one-time codes are the primary method. Apple sign-in is built but stays off until Apple Developer enrolment. Passkeys wait for Supabase support in its JavaScript SDK.

### D-10 · Security baseline (multiple choice)

- **Prompt:** Which extra protections belong in the v1 security baseline?
- **Options:** Encrypted on-device DB · App lock (biometric/PIN) · TOTP two-factor · Server-side audit log
- **Decision:** All four (maintainer).
- **Action:**
  - Encrypted on-device database: SQLCipher on mobile.
  - Biometric/PIN app lock on mobile; inactivity lock on web.
  - Optional TOTP multi-factor authentication.
  - Audit triggers in Postgres that clients can't write to.

### D-11 · Web hosting

- **Prompt:** Where should the web app be hosted?
- **Options:** ★ Cloudflare Workers · Vercel · Netlify · GitHub Pages
- **Decision:** Cloudflare Workers (maintainer).
- **Action:** Static assets on Cloudflare Workers, with security headers (CSP, HSTS) and preview deploys for each PR.

### D-12 · Running cost

- **Prompt:** What monthly running cost is acceptable for the personal instance?
- **Options:** ★ $0, free tiers · up to about $10 · about $25–35 · whatever is needed
- **Decision:** $0, free tiers (maintainer).
- **Action:** Free tiers throughout. Because the free database tier has no backups, encrypted backups are a gate before any real data is entered.
- **Lesson:** "Free" has hidden costs: no backups, projects that pause when idle, email limits. Write them down as risks with mitigations.

## Round 4: product foundations

### D-13 · Currency

- **Prompt:** How should currencies work? (Money is always integer minor units plus an ISO 4217 code.)
- **Options:** ★ Multi-currency accounts · One currency per ledger · Single currency everywhere
- **Decision:** Multi-currency accounts (maintainer).
- **Action:** Each account has its own currency, and each ledger has a base currency for totals.
- **Lesson:** Never store money as floating point. Use integer minor units plus a currency code, and make currency conversion explicit, recording the rate and its date.

### D-14 · Languages

- **Prompt:** Which languages should the app support?
- **Options:** ★ English, i18n-ready · English + Sinhala + Tamil · English only, no i18n
- **Decision:** English, i18n-ready (maintainer).
- **Action:** Every UI string goes through translation files, and numbers and dates use locale-aware formatting.

### D-15 · Telemetry

- **Prompt:** Should the app report crashes and errors? Telemetry from a finance app must never include financial data.
- **Options:** ★ Sentry, scrubbed, can opt out · self-hosted GlitchTip · no telemetry
- **Decision:** Sentry, scrubbed, can opt out (maintainer).
- **Action:** Tests will enforce that financial data is scrubbed before any event is sent. Users and self-hosters can switch it off.

### D-16 · UI and styling

- **Prompt:** Which UI and styling foundation should render iOS, Android and web from one codebase?
- **Options:** ★ Tailwind + React Native Reusables · Tamagui · Unistyles 3 · React Native Paper
- **Decision:** Tailwind + React Native Reusables (maintainer).
